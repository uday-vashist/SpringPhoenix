Why 3 Subagents Instead of One?

Running all 5 modernization phases inside a single AI context causes catastrophic context bloat. Thousands of lines of JaCoCo coverage matrices, Surefire XML outputs, PITest bytecode mutant logs, and terminal stack traces saturate token windows — causing hallucinations and degraded code quality. SpringPhoenix isolates each phase into a dedicated Bob 2.0 subagent with a clean, sandboxed workspace and focused tool access.

Modernized UserService.java

@Service
@Transactional(readOnly = true)   // ← added: disables dirty-check on reads
public class UserService {

    private final UserRepository userRepository;

    public UserService(UserRepository userRepository) {
        this.userRepository = userRepository;
    }

    public List<User> getAllUsers()             { return userRepository.findAll(); }
    public Optional<User> getUserById(Long id) { return userRepository.findById(id); }

    @Transactional
    public User saveUser(User user)             { return userRepository.save(user); }

    @Transactional                              // ← new method: was missing in legacy
    public Optional<User> updateUser(Long id, User userDetails) {
        return userRepository.findById(id).map(existing -> {
            existing.setUsername(userDetails.getUsername());
            existing.setEmail(userDetails.getEmail());
            return userRepository.save(existing);
        });
    }

    @Transactional
    public void deleteUser(Long id)             { userRepository.deleteById(id); }
}

How Gaps Are Detected

All three subagents run a parallel business-logic scanner alongside their primary task. If a method's purpose isn't inferable from its name, comments, or surrounding context, it is flagged — never silently documented with a guess. Flagged items land in reports/knowledge_gaps.md with file path, method name, why it's unclear, and a suggested reviewer question.

1. User.equals(Object o)
src/main/java/com/example/legacy/model/User.java
Uses surrogate-key-only equality: two entities with the same field values but null IDs (transient, not yet persisted) are not considered equal. This is a documented JPA pattern but creates surprising behavior in Set/HashMap use before first persist. Reviewer question: Is the intent to never treat two unsaved Users as equal, or should natural-key equality (username + email) apply to transient instances?
2. User.hashCode()
src/main/java/com/example/legacy/model/User.java
Returns Objects.hashCode(id), which evaluates to 0 for all transient (unsaved) User instances. All transient users collide into the same bucket in any hash-based collection. This is a documented JPA constraint but can cause silent performance degradation if Users are stored in Sets before persistence. Reviewer question: Is the hash-bucket collision acceptable, or should transient Users use a natural-key hash as a fallback?
3. UserService.deleteUser(Long id)
src/main/java/com/example/legacy/service/UserService.java:63
Calls deleteById without first checking whether the entity exists. Spring Data's deleteById silently no-ops on a missing ID — it does not throw an exception by default. The API caller receives HTTP 204 No Content regardless of whether a record was actually deleted. Reviewer question: Should DELETE /api/users/{id} return HTTP 404 when the user doesn't exist, or is 204-always the intentional contract?
